Architectural Blueprint for an Autonomous SWE-Agent Code Editor
I. Strategic Overview and Agent Architecture Foundation
The development of an autonomous Software Engineering Agent (SWE-Agent), often referred to as an Agentic Code Editor (ACE) akin to Devin or AntiGravity , necessitates a robust, multi-component architecture that transcends traditional reactive coding assistants. This system must exhibit true autonomy, enabling it to execute complex, multi-step solutions, manage its internal state, and iteratively refine its work through self-correction and testing. The goal is to create a digital worker capable of independent operation within the GitHub pull request workflow.   

1.1. Defining the Autonomous SWE-Agent: Core Capabilities and Competitive Benchmarks
Autonomous agents are distinguished by their capacity for proactive goal pursuit, reactivity to environmental changes, and independent decision-making, differentiating them significantly from rule-based bots or reactive AI assistants. An ACE must be able to maintain a mental thread of its overarching goal, check its own work, and manage multi-file changes and external dependencies.   

Autonomy and Resilience
Achieving the required level of agent autonomy relies heavily on architectural resilience. While traditional LLM interactions are inherently ephemeral, complex coding tasks demand durability. A sophisticated workflow requires many sequential steps, making the entire process vulnerable to transient failures such as network latency, rate limits, or sandbox timeouts. For the ACE to function as a dependable collaborator, it must be architected with durable execution primitives. This means the system must reliably capture and persist its workflow state, memory, and plan, allowing it to seamlessly continue operation from the latest completed step, even after a crash or interruption. This durability is crucial for scaling the agent from a localized prototype to a resilient, scalable platform capable of handling extended, multi-day development tasks.   

Plan Transparency and Traceability
A central design requirement for any advanced SWE-Agent is the legibility of its planning process. The agent’s decision-making must be transparent not only to aid human debugging but also to comply with secure development practices. The system operates in a sandboxed environment and typically pushes changes to temporary, agent-created branches (e.g., copilot/*), ensuring that all pull requests require independent human review and that commits are co-authored for clear traceability. This requirement mandates that the agent’s internal planning—the interleaved thoughts and actions—are logged and presented clearly, typically within workflow artifacts like the walkthrough.md file.   

1.2. The Foundational Agent Architecture: Profile, Memory, Planning, and Action Modules
The architecture of the SWE-Agent is structured upon four interconnected core components, mirroring the functional organization of intelligent agents in AI literature.   

Profiling/Perception Module: This module functions as the agent's sensory interface, responsible for ingesting and structuring environmental data. It processes the user's initial request, monitors file system changes, and analyzes terminal output and stack traces from the execution environment. This raw data is transformed into a structured context suitable for consumption by the LLM core.

Memory Module (H-RAG): Serving as the knowledge repository, the Memory Module organizes and stores data crucial for goal-oriented behavior. This includes short-term working memory (e.g., the current ReAct trace and recently applied diffs) and long-term knowledge, specifically the structurally indexed codebase context (detailed in Section II). Memory informs both the planning and action processes by providing historical context and learned patterns.   

Planning Module (ReAct Core): This is the strategic center of the agent. It utilizes the ReAct framework to synthesize inputs from the Memory and Perception modules, formulate decisions, and direct sequences of actions toward the overall objective. The planning process is continuous, incorporating feedback from tool execution to maintain and update the action plan.   

Action Module: The execution interface that translates the LLM's planned actions into external operations. This module handles API calls to the sandboxed file system, code execution environment, and artifact generation tools.   

The synergistic operation of these four components ensures a dynamic system where the agent can learn and adapt, make informed decisions based on accumulated experience, and execute complex tasks with high efficiency.   

1.3. Onboarding the Agent: Utilizing AGENTS.md for Persistent Context
A critical consideration in agent architecture is addressing the inherent statelessness of LLMs. An agent begins each session knowing nothing about the codebase unless explicitly provided with context. To overcome this limitation and mitigate context dilution, the system must enforce the injection of high-level architectural context at the start of every session.   

This is accomplished via a foundational context document, often named AGENTS.md (or CLAUDE.md in some contexts), which serves as a persistent, project-specific system prompt. This document must systematically cover three critical knowledge domains:   

WHAT: The technical stack, architectural patterns, and the project's overall structure, including a codebase map that guides the agent on where to look for specific functionalities.   

WHY: The purpose of the project and the function of different modules within the repository, providing essential background for high-level decision-making.   

HOW: The operational procedures, such as specific commands required to run tests, perform type-checking, compile, or execute code.   

By mandating the use of this standardized onboarding document, the agent is provided with a consistent, summarized understanding of the project's ecosystem, allowing it to initiate meaningful work immediately without suffering from the typical overhead of codebase exploration.   

II. Deep Context Management: The Agent's Memory (Hybrid Retrieval-Augmented Generation, H-RAG)
Effective code modification requires the agent to "remember" the entire codebase structure, including architectural patterns, dependencies, and style conventions. Traditional Retrieval-Augmented Generation (RAG) using simple text chunking is inadequate for complex software repositories, often leading to code generation that is contextually inaccurate or isolated from existing dependencies. Therefore, the Memory Module implements a sophisticated Hybrid RAG (H-RAG) approach that combines semantic understanding with structural and lexical knowledge.   

2.1. The Code Ingestion Pipeline: Structured Parsing via Abstract Syntax Trees (AST)
The foundation of high-fidelity code indexing is the transformation of raw source code into structured representations. Reliance on arbitrary text splits introduces ambiguity; instead, the ingestion pipeline must utilize structural parsing.   

AST Tooling and Chunking Strategy
The process begins with parsing the source code into an Abstract Syntax Tree (AST) or Concrete Syntax Tree (CST). Tree-sitter is the recommended tool for this process due to its language-agnostic capabilities, robustness in the presence of syntax errors, and efficient incremental parsing, which is critical for updating the codebase index rapidly as the agent makes edits. The output of the AST parsing dictates the chunking strategy, ensuring that code is segmented based on logical, functionally complete units (e.g., specific classes, methods, or functions), rather than line counts or token limits. This structural chunking guarantees that retrieved snippets are syntactically and semantically coherent.   

Context Engineering Metadata
During ingestion, essential metadata must be extracted and attached to each structured code chunk. This metadata includes the file path, the function signature, the language used, and versioning constraints. This contextual data serves a dual purpose: first, it aids the LLM in understanding the location and purpose of the retrieved code, and second, it acts as high-precision filtering criteria during the retrieval phase, ensuring that the agent's attention is focused only on relevant information, mitigating the issue of competing for limited AI attention.   

2.2. Semantic Context Retrieval: Vector Databases and Code Embeddings
Once parsed and structured, the code chunks are processed for semantic retrieval. Vector databases are specialized systems designed to store, manage, and retrieve high-dimensional data efficiently, making them integral to modern LLM applications.   

Embedding Process and Use Cases
The AST-derived code chunks are converted into numerical vector embeddings, which are then indexed by the Vector Database. This allows the system to perform fast similarity searches and nearest-neighbor queries based on semantic meaning. This capability is highly effective for responding to conceptual queries, such such as retrieving implementations related to a high-level requirement or identifying similar logic across different parts of the codebase. Augmenting the LLM's prompt with this vector-retrieved context enables highly nuanced and context-aware code generation.   

2.3. Structural Context Retrieval: Knowledge Graphs for Dependency Mapping
Semantic similarity alone is insufficient for tasks requiring architectural awareness, such as refactoring or tracing data flow. A robust SWE-Agent must understand how components interrelate. This requires a Knowledge Graph (KG).   

KG Construction and Hybrid Retrieval
The KG is built by transforming the code repository into a graph structure where nodes represent code entities (like classes, functions, and variables) and edges define their relationships (e.g., function calls, API dependencies, inheritance). The ultimate context retrieval mechanism must, therefore, be hybrid, combining semantic hits from the Vector DB with structural traversal of the KG. For instance, if an agent is tasked with modifying a core function, a query routed to the KG can immediately reveal all downstream dependencies. Retrieving this sub-graph context ensures the LLM understands the propagation of changes, guaranteeing that the proposed code modification is contextually accurate and dependency-aware across the entire repository.   

The architecture requires a crucial component: a "Context Router" integrated into the codebase_search tool. The agent's internal deliberation (its Thought) must dynamically dictate the type of retrieval needed (semantic, structural, or lexical). For example, if the agent detects a compile error, it requests lexical context; if it plans a refactor, it requests dependency graph context. This dynamic routing focuses the retrieval and prevents the introduction of irrelevant information into the prompt, thereby avoiding the dilution of the LLM’s limited attention capacity.   

Furthermore, the Knowledge Graph serves an active role beyond passive retrieval. By mapping dependencies, the KG allows the Planning Module to proactively anticipate secondary effects of a proposed change. Before the agent executes a code modification (filesystem_write), it must consult the KG. If the KG indicates that modifying Function X will affect Functions A and B, the agent's plan must be updated before generation to explicitly include necessary corresponding changes to A and B. This transforms the KG into an active constraint enforcement tool, guiding the agent toward architecturally sound and dependency-compliant solutions.

III. The ReAct Decision Engine and Control Flow
The mandatory integration of the ReAct (Reasoning and Acting) framework provides the necessary structure for the agent's Planning Module, ensuring complex tasks are handled through transparent, iterative steps. ReAct is the mechanism by which the agent generates reasoning traces and task-specific actions in an interleaved manner, mirroring human problem-solving through an inner monologue.   

3.1. ReAct Principles for Complex Coding Tasks
ReAct is fundamentally an iterative cycle designed to improve reliability and address issues like fact hallucination inherent in simpler LLM workflows.   

The Paradigm: The agent continuously loops through a structured sequence:

Thought: The LLM analyzes the current state, memory, and task goal, formulating a natural language justification and step-by-step plan (Chain-of-Thought).   

Action: The LLM selects and calls a specific external tool (from its defined Action Space) with structured inputs.   

Observation: The result returned by the executed tool (e.g., retrieved file content, terminal output, or execution status).   

This process continues until the agent determines that the task is complete and verifiable. The generated Thought trace is essential, providing full human interpretability of the agent’s logic during multi-step processes like multi-file refactoring or deep debugging.   

3.2. Defining the Agent's Action Space (Tool API Specification)
To ensure reliable interaction with the environment, the agent requires a concrete, constrained toolset defined through function calling schemas. These tools constitute the agent's capability envelope.   

Table: Toolset Specification for the SWE-Agent

Tool Name	Function	Action Input Schema	Observation Output
filesystem_read	Retrieves specific file content (or a defined range of lines).	{"path": "string", "start_line": "integer", "end_line": "integer"}	{"content": "string", "checksum": "string", "truncated": "boolean"}
codebase_search	Executes the Hybrid RAG query (Semantic/Structural/Lexical).	{"query": "string", "context_type": "enum (semantic/dependency/lexical)", "limit": "integer"}	{"retrieved_snippets": "array of objects", "summary": "string"}
terminal_execute	Runs a command in the sandboxed environment and waits for completion.	{"command": "string", "timeout": "integer"}	{"stdout_summary": "string", "stderr_summary": "string", "exit_code": "integer"}

3.3. ReAct Prompt Engineering and Output Reliability
The prompt template must enforce the ReAct structure while maintaining resilience against common LLM generation failures. A hybrid prompt structure, utilizing XML tags for clear segmentation, Markdown for human-readable instructions, and JSON schemas for machine-parsable tool inputs, optimizes reliability and consistency. The agent is explicitly instructed to follow the established action format.   

Enforcing Structured Output Resilience
Despite careful prompt engineering, LLMs can occasionally generate responses that fail to conform to the required structured format (e.g., invalid JSON in the Action Input), leading to critical parsing errors and workflow failure. The system architecture must account for this by implementing a rigorous validation layer within the Orchestrator. If the LLM output fails validation, the Orchestrator avoids executing the tool externally. Instead, it generates an internal, non-observable corrective observation that details the parsing failure and feeds it back to the LLM. This forces the agent to self-correct the action structure and re-attempt the step, ensuring the agent remains robust against transient generative errors without failing the overall task.   

The Importance of Diff-based Writing
The filesystem_write tool is strictly designed to accept unified diffs or patch formats rather than allowing the LLM to output entire file contents. This approach is paramount for two reasons: minimizing the risk of accidental large-scale deletions, and creating an easily auditable trail of changes. Consequently, the agent's internal planning must reflect this constraint. The planning module must generate a Thought that focuses on "generating a patch for lines X-Y in file Z" rather than merely replacing content. The Observation confirms the successful application of the diff and reports the number of lines modified, thereby feeding essential verification data back into the loop and ensuring accountability for every change.   

IV. The Autonomous Execution and Debugging Workflow
The ability to execute generated code, ingest errors, and autonomously initiate iterative fixes is the defining feature of a modern SWE-Agent. This requires a dedicated sandboxed environment and a sophisticated mechanism for error analysis.   

4.1. Sandboxing and Execution: The Operational Environment
Code execution must be performed in a secure, isolated environment to prevent malicious or accidental system damage. This sandboxed approach is critical for maintaining security, ensuring the agent operates with restricted repository permissions.   

The terminal_execute tool serves as the sole interface to this environment. This tool captures the critical outputs of any command run: the standard output (stdout), the standard error (stderr), and the numerical exit code (exit_code). A zero exit code is the standard signal for success; any non-zero exit code triggers the subsequent debugging sequence.   

4.2. Analysis-Augmented Generation (AAG) for Error Handling
Raw stack traces from the terminal are often verbose and exceed the context window limitations of the LLM, leading to confusion and poor diagnostic quality. To convert this noisy data into actionable intelligence, an Analysis-Augmented Generation (AAG) process is implemented.   

The Error Summarization Function
If the terminal_execute tool returns a non-zero exit code, the raw stderr is immediately forwarded to a dedicated AAG node. This node utilizes a specialized auxiliary LLM call or prompt chain dedicated exclusively to error parsing and summarization. The function of this node is to distill the voluminous stack trace into a concise diagnostic summary, clearly identifying the exception type, the failing file, and the precise line number involved.   

This summarized diagnosis, along with the non-zero exit code, constitutes the primary Observation returned to the main ReAct loop. This targeted feedback mechanism forces the Planning Module to focus its subsequent Thought on the critical failure points, avoiding the prompt dilution that results from attempting to process the entire raw trace.   

4.3. The Iterative Fix Loop and Convergence Strategy
The SWE-Agent operates in a continuous, iterative fix loop when errors are encountered. This debugging sub-loop requires careful orchestration to maximize effectiveness while ensuring convergence.   

Iterative Cycle Structure
Upon receiving a failure Observation (the AAG Summary), the agent executes the following refinement cycle:

Thought: Analyze the AAG summary against the codebase context and propose an initial hypothesis for the cause.

Action: codebase_search: Use the file/line details from the AAG summary to query the H-RAG system, specifically requesting structural or lexical context around the point of failure.

Observation: Retrieved relevant code snippets from the H-RAG (Section II).

Thought: Formulate a detailed corrective patch based on the gathered context.

Action: filesystem_write: Apply the generated diff/patch to the relevant file(s).

Action: terminal_execute: Re-run the verification command (e.g., tests or build).

Observation: Receive new results (success or failure) and restart the process if necessary.

Contextual Awareness in Debugging
To ensure successful iteration, the system must integrate awareness of recent changes. When an error occurs, the AAG Summary and the latest error trace must be analyzed alongside the Memory Module's short-term context, which tracks all previously applied diffs within the current task. This allows the agent to immediately determine if the error was introduced by its immediately preceding action, enabling a focused self-correction or, if necessary, an immediate rollback of the last patch, enhancing the efficiency of the debugging loop.

Convergence and Loop Mitigation
Autonomous debugging must be governed by explicit termination criteria to prevent the agent from entering an endless "fix loop" where it repeats or cycles through ineffective changes.   

Success Condition: The loop terminates immediately upon receiving an Observation indicating an exit_code of 0.

Maximum Iterations: A strict ceiling (e.g., 5-8 attempts) must be imposed. If this limit is reached, the agent terminates the task as a failure and generates a mandatory walkthrough.md documenting the stalemate.

Quality Check/Stalemate Avoidance: To prevent the agent from proposing identical or trivial fixes, the system requires the LLM to explicitly justify, in its Thought component, why the next proposed fix attempt is fundamentally different and structurally superior to the last one. If the proposed fix re-introduces a previously tried solution, the Orchestrator interrupts the process and declares a non-convergent loop.   

A crucial element in defining success is linking the LLM's output directly to predefined standards. The initial implementation_plan.md (Section V) contains explicit, measurable Acceptance Criteria (AC). The agent's final Thought before declaring success must explicitly reference these ACs, stating how the code changes and test results meet the required quality standards. This uses the agent’s own output specification to define the criteria for convergence.   

V. Structured Workflow Artifacts: Task-Driven Development
A key requirement, modeled after the sophisticated workflows used by autonomous agents like AntiGravity, is the generation and use of structured markdown artifacts. These files (implementation_plan.md, task.md, and walkthrough.md) provide the required framework for planning, execution, traceability, and human handoff. The artifact_generate tool is responsible for reliably producing these files according to predefined schemas.   

5.1. Orchestration Framework and Artifact Generation
The agentic workflow begins with the LLM transforming the user request into a comprehensive plan (implementation_plan.md). This plan is then systematically broken down into discrete, manageable, and testable chunks—the atomic tasks defined in task.md. Upon completion, success, or failure, the execution details are summarized in walkthrough.md. This structured approach ensures that specifications are ready for implementation before delegation to the coding agent.   

5.2. Detailed Schemas for Workflow Files (.md Artifacts)
These artifacts utilize Markdown for human readability, combined with structured data formats (like embedded XML or JSON) for machine parsing and process automation.   

implementation_plan.md: The Blueprint
This artifact is generated during the initial planning phase and details the high-level strategy and architectural considerations. It acts as the contract for the task.   

XML
<ImplementationPlan>
  <ExecutiveSummary>Concise overview of feature purpose and goals.</ExecutiveSummary>
  <Architecture>Architecture design and component relationships.</Architecture>
  <DataModels>Data schemas, relationships, and API specifications (if applicable).</DataModels>
  <Milestones>Logical, incremental development stages.</Milestones>
  <TestingStrategy>Testing approach, coverage expectations, and measurable Acceptance Criteria (AC).</TestingStrategy>
  <ImplementationConsiderations>Error handling strategies and scalability notes.</ImplementationConsiderations>
</ImplementationPlan>
task.md: The Checklist
The plan is broken down into this list of discrete, actionable tasks. Each task must be verifiable and atomic. This file is the agent's immediate execution roadmap.   

JSON
,
    "verification_command": "python tests/unit/test_processor.py::test_retry_logic",
    "dependency_ids":,
    "status": "PENDING"
  },
  {
    "id": "T2",
    "description": "Update payment handler to call 'retry_payment' on failure.",
    "files_affected": ["src/api/handler.py"],
    "verification_command": "make integration_test_payment_flow",
    "dependency_ids":,
    "status": "PENDING"
  }
]
The verification_command field establishes a direct execution contract. A task is only marked DONE if the agent executes this specific command via the terminal_execute tool, and the resulting exit_code is zero. This rigorously links structured planning to successful execution validation.

walkthrough.md: The Documentation
This final artifact records what was actually done and is generated regardless of task success or failure. It serves as the comprehensive audit log and the primary document for human handoff.   

The walkthrough.md must be engineered for rapid human ingestion, especially in cases where the agent failed. It includes an executive summary, generated by the LLM post-execution, that succinctly answers: What was the objective? What changes were applied? What was the final result? And critically, if failure occurred, where did the fix loop terminate and what is the recommended next step for a human developer?

XML
<Walkthrough>
  <Summary>Task T1 completed successfully after 2 self-correction iterations.</Summary>
  <Results>
    <VerificationStatus>SUCCESS (exit code 0)</VerificationStatus>
    <FinalTestOutput>Log of final successful test run.</FinalTestOutput>
  </Results>
  <DiffsApplied>
    Details of all patches applied during the task execution (sourced from filesystem_write observations).
  </DiffsApplied>
  <FullReActLog>
    (The complete, verbose log of all interleaved Thought-Action-Observation steps.)
  </FullReActLog>
</Walkthrough>
VI. Step-by-Step Implementation Roadmap
The deployment of the autonomous SWE-Agent follows a phased development approach, prioritizing the establishment of the deep context foundation before integrating the complex, stateful control flow mechanisms.

6.1. Phase 1: Context Ingestion and Memory Setup (H-RAG Foundation)
This phase establishes the agent's ability to "see" and "remember" the codebase structure accurately.

Step	Focus Area	Key Deliverable
1.1	Environment Setup	Implementation of the sandboxed terminal interface with a minimal terminal_execute tool capable of basic command I/O.
1.2	Code Profiling	Integration of the Tree-sitter parser to generate Abstract Syntax Trees (ASTs). Development of the chunking logic based on structural units (functions, classes).
1.3	Semantic Indexing	Setup of the Vector Database. Implementation of the embedding pipeline and the initial vector-only version of the codebase_search tool.
1.4	Structural Indexing	Setup of the Graph Database. Development of scripts to populate the graph with dependency relationships derived from the AST (e.g., function call graphs, import tracking).
1.5	Onboarding Context	Finalization and testing of the mechanism for context injection of the AGENTS.md file into the initial LLM system prompt for every session.
6.2. Phase 2: Tool Integration and ReAct Core Loop
This phase focuses on defining the agent's action capabilities and establishing the robust, self-correcting decision-making process.

Step	Focus Area	Key Deliverable
2.1	Agent Identity	Finalization of the system prompt, including role, constraints, and the mandated ReAct template.
2.2	Action Tools	Implementation of robust filesystem_read and filesystem_write tools, strictly enforcing the use of unified diff/patch formats for writing.
2.3	ReAct Prompting	Development and unit testing of the ReAct prompt structure, ensuring the LLM reliably alternates between Thought, Action, and Observation states.
2.4	Orchestrator Resilience	Implementation of the Orchestrator layer's parsing error fallback loop. This ensures internal self-healing by detecting invalid tool outputs and forcing the LLM to regenerate the correct structure before execution.
2.5	Artifact Generation	Implementation of the artifact_generate tool, tested to reliably output structured files (implementation_plan.md, task.md, walkthrough.md) according to the defined JSON/XML schemas.
6.3. Phase 3: Iterative Execution and Workflow Automation (Autonomy Layer)
The final phase integrates all components to achieve full autonomy, focusing on strategic planning, robust debugging, and auditability.

Step	Focus Area	Key Deliverable
3.1	Planning Automation	Validation that the LLM can generate a high-quality implementation_plan.md from a natural language request and subsequently break it down into an executable, verifiable task.md checklist.
3.2	Analysis-Augmentation	Deployment and testing of the dedicated AAG node for automated, concise error summarization from raw stderr output.
3.3	Debugging Loop Control	Implementation of the full set of convergence criteria, including setting the maximum iteration limit, integrating the change justification requirement in the ReAct Thought, and ensuring the agent tracks temporal context (recent diffs).
3.4	Workflow Documentation	Finalized end-to-end generation of walkthrough.md that accurately logs all ReAct steps, applied diffs, and the final verification status (whether success or documented failure).
3.5	End-to-End Validation	Comprehensive testing of the agent on complex, multi-file tasks that necessitate H-RAG context retrieval, test execution, dependency-aware code modification, and autonomous error debugging.
VII. Conclusions and Recommendations
The creation of a highly autonomous SWE-Agent requires transitioning from simple reactive AI assistants to a sophisticated, architecturally sound system built upon durability, structured memory, and reflective planning.

The most crucial recommendation for this implementation is the mandatory adoption of a Hybrid Retrieval-Augmented Generation (H-RAG) system. Relying solely on semantic text retrieval will lead to architectural failures and dependency breaches in complex codebases. The integration of AST parsing (via tools like Tree-sitter) feeding both a Vector Database (for conceptual retrieval) and a Knowledge Graph (for structural and dependency mapping) is essential to provide the LLM with the context necessary to propose architecturally safe and relevant code modifications.   

Furthermore, the agent's control loop must be defined by the ReAct paradigm, which enforces transparent, step-by-step reasoning and action. To ensure this agent is practical and reliable, architectural provisions must be made for systemic resilience:   

Durable State Management: The complexity of coding tasks demands that the agent's state persists beyond a single session or a transient failure. The choice of underlying execution platform must support durable execution primitives to allow the agent to resume its task reliably.   

Structured Debugging: Debugging must move beyond simply dumping stack traces into the prompt. The mandatory implementation of an Analysis-Augmented Generation (AAG) node for error summarization ensures that the agent receives focused, high-signal feedback, leading to targeted and efficient iterative fixes.   

Auditable Artifacts: The use of structured files—the implementation_plan.md, task.md, and walkthrough.md—establishes a rigorous, auditable workflow. This not only guides the agent but ensures plan transparency, which is vital for human review and necessary for security protocols that govern autonomous code contributions. The verification contract within task.md ensures that success is defined by executable proof (exit code 0) rather than mere subjective completion.
